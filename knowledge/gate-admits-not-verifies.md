# 閘門擋住壞的，不等於放進來的是對的

## 形狀

倒推驗證一條產出鏈時，走到某張表，看到它有守衛（trigger／constraint／
schema check），確認守衛會拒絕不合格的輸入——然後**這一跳就被記成通過了**。

漏掉的是：守衛回答的是「**沒有壞的進來**」，
沒有回答「**進來的這一筆是不是它自稱的那一筆**」。

必要條件與充分條件在看板上長得一模一樣：兩者都是一個綠燈。

## 實測

某平台的預測發布路徑：資料庫 trigger 保證只有「勝過基準的 model_run」
才能被寫進 `forecast`，而且 `beats_baselines` 是 GENERATED 欄位，
沒有人能手寫 true。這條守衛是真的，也真的在擋。

倒推停在這裡。打開**寫這張表的那支程式**之後，發現三件事：

1. 發布端**寫死一種模型**去重擬合，不管贏的是哪一個演算法；
   贏家的超參用 `get(key, default)` 讀 → 換模型的那天，
   發布出去的會是 A 的擬合結果，掛著 B 的 id 和 B 的分數。
2. 選最佳候選時**跨資料版本比分數**，而不同資料版本的折數不同，
   兩個數字印起來一樣長、意思不一樣。
3. 訓練目標的約定（預測「值」還是「變化」）只被記在自由文字欄的句尾，
   發布端從來沒讀，無條件當成其中一種。

三件事今天都沒有造成錯誤的產出——**因為另一個模型剛好輸了**。
不是規則擋下來的，是運氣。

## 判準

倒推的每一跳，要分開問兩個問題：

- **這一跳擋掉了什麼？**（守衛）
- **這一跳寫進去的是誰寫的、用什麼寫的？**（生產者）

只回答第一個就記成通過，等於承認「沒有壞的」就是「是對的」。

**具體做法**：每到一張有守衛的表，打開它的**唯一寫入者**，
逐行對照「這張表上的每一欄，是不是真的由它宣稱的來源產生」。
特別注意 `get(key, default)` 這種讀法——它把「缺欄位」變成「合法的預設值」，
而缺的那個欄位往往正是身分。
