# 被推翻的知識：標記取代，不要刪除

- AIS 共用知識層目前有兩種過期機制：`ttl_days`（宣稱本身有效期到了）與 source digest 漂移（來源真的變了）。兩者都只能表達**「這條可能不準了」**。
- 它們表達不了的是：**「這條被哪一條推翻了、從哪一天起」**。而推翻正是這個專案最常發生的事——一個實測結論被下一次實測改寫。
- 業界已驗證的做法是**雙時間軸**（Zep/Graphiti，Apache-2.0）：每個事實帶一個有效區間——何時成為真、何時（若曾）被取代。衝突時**標記失效不刪除**，保留完整可稽核的沿革，並可查詢「在任一時間點，當時認為什麼是真的」。
- **分層決定（2026-08-29 修正）**：先做 schema 的兩個欄位（`valid_from` / `superseded_by`）與一條取代關係，**圖層留在路線圖上而不是排除掉**。
  - 初版寫的是「不要引入圖資料庫」，那句話在共用層只有 14 筆 record 時成立，但它把**現在不需要**講成了**以後也不需要**——這正是本 record 自己在講的錯誤（把當下前提下的結論寫成永久事實）。使用者當場指出，判斷改回：先後順序問題，不是取捨問題。
  - 順序的理由：攝入層（`session-ingest`，2026-08-29 實測 114 會話 / 21737 訊息）證明了資料量會成長到單靠 YAML record 撐不住。但**先建圖再想要查什麼，會得到一個沒人查的圖**。Kuzu 是嵌入式、無 server（符合 §5c，不像 Neo4j 要常駐行程），適合當**衍生投影**：等真的出現需要圖遍歷的查詢（例如「這條結論被哪幾條推翻、沿革怎麼走」）再從 SQLite/YAML 這個可重建的 SSoT 長出來。
  - Graphiti 本體同理：它的雙時間軸與失效傳播是成熟實作，規模到了就該用，而不是自己重寫一個半殘的。
- 為什麼「不刪除」重要：刪掉被推翻的結論之後，下一個人（或下一隻 AI）會用同樣的理由重新推導出同一個錯誤，因為推翻的證據已經不在了。這個專案已經有實例——制度記憶把「codegraph 已移除」寫成既成事實，而實際沒有。
- **2026-08-29 第二個實例（同一條殭屍，更強的證據）**：2026-08-11 清掉 3 處 codegraph 設定後，紀錄寫的是「已清除」。今天在 `~/.kiro/settings/mcp.json` 找到**第 4 處**，而且 kiro-cli 每次啟動都印 `One or more mcp server did not load correctly` 卻仍回 rc=0——廠商自己也把它靜默化了。它躲過偵測不是因為偵測邏輯壞了，是因為 **kiro 不在手維護的掃描名單上**。這正說明「已清除」這種宣稱需要的不只是時間戳，而是**當時的掃描範圍**：同一句話在 6 家的範圍下為真，在 12 家的範圍下為假。`valid_from` 要記的不只是何時成立，還有**在什麼前提下成立**。
