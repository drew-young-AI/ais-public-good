# 一筆的註冊表不是擴充性

## 形狀

重構把寫死的相依改成註冊表／plugin／strategy，然後**只登記原本那一個**。

從此：
- 介面看起來是可擴充的
- 文件可以誠實地說「加一筆就好」
- **而那條路徑從來沒有被走過一次**

第二筆被加進去的那天，才會發現介面漏掉了必要的欄位、
呼叫端有隱含假設、或是顯示層根本分不出兩者。

## 實測

某平台的資料庫 schema 從第一天就有 `algorithm`／`hyperparams`／`seed`
——一個說「支援很多模型」的結構。程式碼裡只有一個模型，
而它的身分被**手抄成四份**（兩個建構子、一行 banner、一段 INSERT）。
漏改任何一處，紀錄就會用舊模型的名字記新模型的數字。

加入真正的第二個家族之後，**當場暴露一個顯示層的缺陷**：
「最新一次執行」在只有一個實作時是明確的，兩個之後兩者會**輪流佔用同一格**，
板面讀起來像同一個東西時好時壞。這個缺陷不可能在只有一筆時被發現。

## 判準

**第二筆必須是真的**：跑得起來、留下紀錄、數字進得了同一張比較表。
dry-run 的紙上數字不算——它證明的是「不會爆炸」，不是「這條路通」。

**測試的第一條斷言是「有第二筆」**，不是「字典存在」：

```
assert 清單包含 <原本那一個>
assert 清單包含 <第二個>          # 少了這條，整套測試對寫死也會全綠
assert 未登記的名稱被拒絕且列出清單   # 靜默回退＝把 A 的名字記在 B 的數字上
```

**列表指令要跑跟選取路徑同一個守衛**：列得出來的必須是選得起來的，
否則那份清單本身就是一個「登記為存在，但不執行」的目錄。

## 每一筆該宣告什麼

不要只放 factory。把**呼叫端會分歧的前提**變成必填欄位，
缺了就拒絕啟動——這樣第三筆的加入者會被迫回答同樣的問題。

實例中的必填欄位：家族分類（決定兩次執行可不可比）、
輸入限制與對應政策（該案是能不能吃缺值，缺值佔 51.8%）、
以及**是否可重現**（不可重現要能宣告，因為驗收門檻據以判定 `UNVERIFIED`）。
